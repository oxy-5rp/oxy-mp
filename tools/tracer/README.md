# Чтение обфусцированного кода игры в живом процессе

Два коротких орудия, которыми разбирается код `GTA5.exe`. Оба работают по живому
процессу и ничего в нём не меняют.

Нужны они потому, что **на диске код не лежит**. У `GTA5.exe` две секции `.text`,
и настоящая расшифровывается при запуске: поиск сигнатуры по файлу не находит
ничего, и разбирать можно только память запущенной игры.

```powershell
$env:PYTHONIOENCODING = 'utf-8'
python tools\tracer\trace.py 0x7ff66ea1e23e 60   # адрес и предел шагов
python tools\tracer\peek.py 0x7ff66d1cd5f0 0x7ff66d1cd5f4
```

Нужен `capstone` (`pip install capstone`).

## `trace.py` — что код делает на самом деле

Обфускация здесь — расплющенный поток управления: работа разбавлена
переходами-переходниками так, что линейный дизассемблер тонет после третьей
инструкции. Трассировщик идёт по переходам и печатает только работу.

**Два приёма он распутывает, и без них не выходит ничего.**

Первый — обычный `jmp` в чужой конец функции; их тут сотни, и каждый уводит
разбор в мусор, если его не пройти.

Второй хитрее — **подменённый адрес возврата**:

```
push  rsi                     ; занять место
lea   rsi, [rip + смещение]   ; куда на самом деле идём
xchg  qword ptr [rsp], rsi    ; положить это вместо адреса возврата
ret                           ; и «вернуться» туда
```

Это `jmp`, написанный четырьмя инструкциями. Не распутав его, трассировка
обрывается на `ret` в самом начале работы — и выглядит это так, будто функция
ничего не делает.

## `peek.py` — растёт ли число

Читает по четыре байта с названных адресов раз в пять секунд. Нужен затем, чтобы отличить счётчик
от постоянной: у обоих в коде один и тот же вид (`mov ecx, [rip + …]`), а
разница между ними — вся суть вопроса.

## Что этим уже выяснено

`network_bail` — та самая дверь, которой держится сессия (см. `CLAUDE.md`).
Разобрано следующее, и повторять это не нужно:

- у неё два выхода, и они сходятся в общий хвост;
- на ветви «байт состояния взведён» она собирает запись из двух чисел и кладёт её
  в одиночку через виртуальный вызов. Одиночка заводится лениво: 0x1F70 байт, из
  них два кольцевых буфера по 0xFA0 со счётчиками после каждого;
- два числа, которые ложатся в запись, — **постоянные**: 36 и метка сборки.
  Проверено `peek.py` — за пятнадцать секунд игры не изменились ни разу. Значит
  догадка «где-то тикает счётчик, который эта функция сбрасывает» здесь опоры не
  имеет, и искать надо не тут.

То есть похоже это на телеметрию, а не на управление ресурсами. Крах на
восемнадцатой минуте лечится не отсюда — он лечится пропуском (`kRelief`), и это
уже сделано.
